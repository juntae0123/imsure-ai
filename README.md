# IMSURE — 실시간 비대면 보험 상담 AI (AI 파트)

상담사가 **법정 필수 고지 항목을 빠뜨리면 말하는 중에** 감지해 경고하고, 증적 영상의 그 발화 지점에 마커를 남기는 시스템. 이 저장소는 SSAFY 공통 프로젝트(팀 5인, 3주) 중 **AI 파트(STT 파인튜닝 · 고지 누락 판정 엔진 · RAG)의 기록**이다. AI 파트는 단독 담당했다.

> 팀 공동 산출물인 서비스 코드(FE/BE/인프라)는 포함하지 않는다. 여기 있는 것은 **내가 만든 모델·판정 로직의 실험 기록과 설계 판단**이다.

## 결과

| 항목 | 값 |
|---|---|
| STT 파인튜닝 | Whisper-medium 한국어 + LoRA, **실험 11회** |
| CER | **11.7% → 5.43%** (53.6% 개선, valid 500샘플) |
| 순수 인식 오류 (표기 규칙 제외) | 7.61% → **4.85%** |
| 최종 채택 | `exp8` — r=64, q·k·v·o, lr 2e-4, 16k 샘플, beam 5 |
| 판정 게이트 | 키워드 트리거 + 정준문장 임베딩 유사도 **0.58** |
| 고지 항목 | 법정 공통 + 상품별 **2계층**, 세션당 42개 |
| 의사결정 기록 | **D-1 ~ D-13** (`docs/DECISIONS.md`) |

## 이 저장소에서 볼 것

### 1. 내가 낸 결론을 내가 뒤집었다 — `docs/DECISIONS.md` D-13
`exp4` 에서 "용량(LoRA rank)은 병목이 아니다"라고 결론을 냈다. 그런데 valid loss 곡선이 `exp2` 와 함께 학습률 과다를 시사했다. 교란변수를 의심해 **같은 용량(r64, q·k·v·o)에서 LR 만 1e-3 → 2e-4** 로 바꿔 재검증하니 valid 0.338 → 0.2232, CER 8.09% → **5.43%**. 실패의 원인은 용량이 아니라 LR 이었다.

### 2. 표본 부족이 순위를 오판시켰다 — `exp10` / `exp11`
200샘플 평가에서 r128(5.38%)이 r64(5.43%)보다 좋아 보였다. 최종 후보 4개를 **valid 전체 500샘플로 재측정**하니 5.74% vs 5.56% 로 **역전**. 200샘플의 해상도가 0.05%p 차이를 판정할 수 없었다.

### 3. 오류를 분해해 개선 방향을 정했다 — D-11
CER 을 그대로 읽지 않고 구두점·숫자·띄어쓰기 표기 차이와 **순수 인식 오류**로 나눴다. 개선분의 대부분이 표기 규칙 쪽이라는 사실이 이후 판단(전이 가능성·모델 크기 선택)의 근거가 됐다.

### 4. 학습 환경과 서비스 환경의 음향이 달랐다 — D-12
학습 데이터는 전화망(8kHz PSTN, G.711/AMR), 서비스는 브라우저(16kHz WebRTC, Opus). 전이를 가정하지 않고 **서비스와 동일 경로로 A/B 평가셋**을 만들었다(getUserMedia → 16kHz 모노 PCM, 고지 항목 대본 낭독이라 정답 전사 불필요, 같은 녹음을 두 모델에 투입해 장비 차이 상쇄). 한계도 명시했다 — 대본 낭독은 실제 상담보다 쉽다. **전이 판정에는 유효하나 절대 성능 예측에는 쓰지 않는다.**

### 5. 어려운 문제를 풀지 않고 없앴다 — D-2
"음성을 적절한 시점에 나눠야 누락 판단이 가능한데 실시간으로 되는가"라는 우려는 *대화를 구간으로 잘라 검사한다*는 전제에서 나온 것이었다. 세션을 나누지 않고 **체크리스트를 스트리밍 전사에 계속 대조**하도록 재정의했다 → 실시간 세그멘테이션 문제가 해결되는 것이 아니라 **발생하지 않는다**. 상태 크기가 항상 고정(N 플래그 + 타임스탬프)이라 30분 세션에서도 비용이 선형 증가하지 않고, 같은 자료구조가 실시간 경고·영상 마킹·동의 리스트 세 기능에 재사용됐다.

### 6. 증적 마커가 발화 끝을 가리켰다 — `records/진단서_...txt`
마커가 말이 시작된 곳이 아니라 **AI 가 판단을 끝낸 곳**에 찍혔다(2~10초 늦음). 원인은 마커 좌표로 `time.time()`(판정 완료 시각)을 보낸 것. 발화 시작 위치(`audioOffset`)는 STT 단계에서 **이미 계산돼 있었는데 전송 단계에서 버려지고 있었다.** 게다가 그 값을 그냥 쓸 수도 없었다 — `audioOffset` 은 "봇이 듣기 시작한 시점" 기준, 마커는 "녹화 시작" 기준으로 **기준점이 다른 시계가 둘**이었다. 봇 수신 시작 시각을 기록해 두 시계를 정합했다.
