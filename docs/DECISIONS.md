<a id="d-1"></a>
## D-1. 파인튜닝 대상 선정 — "파인튜닝을 하느냐"가 아니라 "무엇을 하느냐"

**상황**
팀에서 "파인튜닝을 해보자"는 방향이 나옴. 데이터셋도 좋아 보인다는 의견.

**검토**
RAG 시스템에서 파인튜닝 대상은 셋으로 갈리고, ROI가 완전히 다르다.

| 대상 | 효과 | 판단 |
|---|---|---|
| 임베딩 | 약관 검색 정확도에 직결 | ROI 최고 |
| LLM | RAG는 검색된 근거를 읽고 정리하는 역할 → 지식을 weight에 굽는 건 방향 오류 | 불필요 |
| STT | 도메인 용어 인식률. 단 오디오+전사 쌍 필요 | 조건부 |

**판단**
- 파인튜닝은 **임베딩 우선**, STT는 도메인 음성 데이터 확보 시 추가, LLM은 제외
- LLM에 지식을 학습시키는 것은 RAG로 푸는 문제이며, 약관 개정 시마다 재학습이 필요하고 할루시네이션 위험만 증가

**근거**
"데이터셋이 좋아 보인다"와 "우리 용도에 맞는다"는 별개다. 파인튜닝 대상마다 필요한 데이터 형태가 다르다.
- 임베딩 튜닝 → (질문, 관련 조항) 쌍
- LLM 튜닝 → (지시, 이상적 답변) 쌍
- RAG 지식베이스 → 원문 (파인튜닝 아님)
- 고지 누락 판정 → 체크리스트 (정답셋이지 학습 데이터 아님)

<a id="d-2"></a>
## D-2. 고지 누락 판정 — 실시간 세션 분할을 없애는 방향으로 재정의

**상황**
팀장 제기: "음성 데이터를 적절한 시점에 나눠야 정확한 누락 판단이 가능한데 실시간으로 가능한가. 설명 순서도 정해야 세션을 나눌 수 있다."

**검토**
이 우려는 "대화를 구간으로 잘라 구간별로 검사한다"는 전제에서 나온다. 실시간 세그멘테이션은 난이도가 높고, 순서 강제는 상담 흐름을 해친다.

**판단**
세션을 나누지 않는다. **계약별 필수 고지 체크리스트를 두고 스트리밍 전사에 계속 대조**하며, 항목이 언급되면 체크 + 타임스탬프를 기록한다.

**근거**
- 실시간 세그멘테이션이라는 어려운 문제가 **해결되는 것이 아니라 발생하지 않는다**
- 설명 순서 검증도 타임스탬프 후처리로 가능해져, 순서 때문에 실시간으로 자를 이유가 사라짐
- 상태 크기가 항상 고정(N개 플래그 + 타임스탬프)이라 30분 세션에서도 비용이 선형 증가하지 않음
- 이 자료구조가 실시간 경고·녹화본 마킹·고객 동의 리스트 세 기능에 그대로 재사용됨

**보완**
순수 키워드 매칭은 패러프레이즈("돈을 잃을 수도")와 부정문("원금 손실은 없습니다")에서 깨진다.
→ 키워드를 빠른 트리거로 쓰고, 항목별 정준 문장과의 임베딩 유사도를 fallback으로 둔다.

<a id="d-3"></a>
## D-3. 판정 타이밍 — 설명 도중에는 판정하지 않는다

**상황**
"키워드 기반이어도 설명 도중에 판정하면 애매하지 않나"라는 반론.

**검토**
애매함은 *아직 하지 않음(pending)* 과 *누락(missed)* 을 같은 상태로 취급할 때 발생한다. 두 문제가 섞여 있었다.
- 매칭 정확도 (패러프레이즈·부정문을 잡느냐)
- 판정 타이밍 (언제 누락이라 부르느냐)

**판단**
상태를 셋으로 분리한다.

| 상태 | 시점 |
|---|---|
| PENDING (회색, "아직") | 설명 중 — **판정하지 않음** |
| COVERED (초록) | STT final에서 매칭 시 |
| MISSING (빨강) | **계약 동의 직전 게이트에서만 확정** |

**근거**
- 실시간 화면은 "판정"이 아니라 "커버리지 진행 현황"이다. 도중에 회색인 것은 아직 그 얘기를 안 했으니 당연하다
- 누락 확정 시점은 상담사가 마무리 단계로 넘어간 뒤이므로 애매함이 없다. 이 게이트는 이미 요구사항(F-6.2 고객 동의 리스트)에 존재했다
- 중간 알림이 필요하면 expected_order를 힌트로 쓴다 (판정이 아니라 리마인더)

<a id="d-4"></a>
## D-4. GPU 인프라 제약 발견 → 아키텍처 역설계

**상황**
팀이 GPU 서버(H200 141GB)를 확보. 초기 설계는 "브라우저 → GPU 서버로 PCM 직송(방식 C)"이었고, 실시간 STT·RAG를 온프레미스로 처리해 금융 음성의 외부 유출을 막는 것이 보안 원칙이었다.

**검토**
서버 사용 가이드를 확인한 결과 세 가지 제약이 드러났다.

| 제약 | 영향 |
|---|---|
| VPN 접속 전용, 공인 IP·포트 개방 불가 | 브라우저가 직접 접속 불가 |
| 세션 24시간 후 프로세스 강제 종료 | 상시 서비스 서버로 부적합 |
| 공용 서버, device만 배정 | 포트 개방 권한 없음 |

추가로, "직접 접속 불가 시 EC2가 중계"라는 기존 대안도 성립하지 않았다. **EC2 역시 VPN 안쪽의 H200에 도달할 수 없기 때문**이다.

**판단**
- 방식 C 폐기
- H200의 역할을 **학습·배치 전용**으로 재정의: 파인튜닝, 임베딩 색인, 사후 정밀 재전사
- 실시간 경로는 API 또는 EC2 CPU로 분리

**근거**
성능(141GB)과 배포 가능성은 별개다. 이 서버는 "학습용 개발 환경"이지 "서비스 인프라"가 아니며, 24시간마다 수동 재기동이 필요하다는 것 자체가 상시 서비스에 쓰지 말라는 신호다.

**검토했으나 채택하지 않은 우회안**

| 우회 | 왜 안 썼나 |
|---|---|
| 터널링(ngrok 등) | 24h 종료는 못 뚫음. 공용 서버 규정 위반 소지 |
| 역방향 연결(H200이 EC2로 아웃바운드) | 기술적으로 가능하나 24h마다 재연결 필요. 시연 안정성을 여기 걸 수 없음 |
| cron 자동 재기동 | 공용 서버 자원 상시 점유 |

3주 프로젝트에서 데모 실패는 전체 손실이므로, 우회는 스트레치로 격리하고 메인 경로는 안정성을 택했다.

<a id="d-5"></a>
## D-5. 실시간 STT를 외부 API로 — 온프레 원칙의 부분 포기

**상황**
D-4로 실시간 추론용 GPU가 없어짐. 선택지는 셋이었다.

| 안 | 내용 | 평가 |
|---|---|---|
| A | 별도 실시간 GPU 확보 | 미제공, 비용 발생 |
| B | 상용/제공 STT API | 즉시 가능, 음성이 외부로 |
| C | EC2 CPU 경량 모델 | 무료지만 느리고 정확도 낮음 |

**판단**
B 채택. 단 보안 원칙을 **범위를 좁혀 재정의**한다.

**근거**
"음성 온프레미스" 원칙이 실시간 구간에서 깨지는 것은 사실이므로 이를 감추지 않고 명시한다. 다만:
- 고객 트랙은 애초에 STT 대상이 아니다(D-12 별도 결정) → 병력·소득 등 민감정보는 외부로 나가지 않음
- 외부로 나가는 것은 상담사의 약관 설명 발화
- 사후 정밀 재전사는 H200 온프레 유지

즉 "전부 온프레" → "민감도가 높은 데이터만 온프레"로 원칙의 적용 범위를 조정했다.

<a id="d-6"></a>
## D-6. whisper-1 스트리밍 불가 → 준실시간 청크로 구조 단순화

**상황**
교육기관 제공 API 크레딧에 포함된 STT는 `whisper-1`. 확인 결과 **배치 모델이라 스트리밍 partial 결과를 내지 못한다.**

**검토**
기능별로 지연 요구가 다르다는 점을 이용했다.

| 기능 | 지연 요구 | whisper-1 |
|---|---|---|
| 고지 누락 판정 | 발화 종료 후 수 초 | 가능 |
| 실시간 자막 | 1초 내외 partial | 불가 |

**판단**
- 판정용 STT는 **VAD로 발화 단위를 잘라 3~5초 조각을 HTTP POST**하는 준실시간 청크 방식
- 실시간 자막은 원래 확장(후순위) 기능이므로 MVP에서 제외

**근거**
이 선택이 오히려 구조를 단순하게 만들었다. **스트리밍 WebSocket 서버가 불필요**해져, 상시 소켓 서버를 어디에 띄울지에 대한 문제가 사라졌다. 제약을 우회한 것이 아니라 제약에 맞춰 요구사항을 정렬한 결과다.

<a id="d-7"></a>
## D-7. 고지 항목 데이터셋 — 법정 공통 + 상품별 2계층

**상황**
"고지 누락 판정"은 정답 리스트가 있어야 성립하는 기능인데, 그 출처가 정의되어 있지 않았다.

**검토**
법령을 조사한 결과 필수 고지 항목이 **명시적으로 열거**되어 있음을 확인했다.
- 금융소비자보호법 제19조 + 시행령 제13조 (보장성 상품 설명 필수사항 4개)
- 상법 제638조의3 (약관 교부·설명의무)
- 「3대 기본지키기」 (청약서 부본 전달 / 약관 설명 / 자필서명)

**판단**
2계층으로 분리한다.

| 계층 | 내용 | 갱신 |
|---|---|---|
| 법정 공통 | 법령 기반. 모든 보장성 상품 공통 | 고정, 재사용 |
| 상품별 | 해당 상품 약관 기반 (보장·면책·지급제한·해약환급금) | 상품마다 교체 |

**설계상 추가 판단**
- 항목마다 `legal_basis`(근거 법령)와 `legal_source`(원문 발췌)를 **필수 필드로 강제**. 판정 근거를 법조문으로 설명할 수 있어야 하고, 키워드·정준문장을 원문에서만 도출해 환각을 차단하기 위함
- 항목을 `STT`(발화로 확인)와 `EVENT`(문서 전달·전자서명으로 확인)로 구분. 청약서 부본 전달과 자필서명은 말이 아니라 행위로 이행되므로 STT 판정 대상이 아님
- `required`/`priority`를 두어 전 항목 필수 시 발생하는 경고 과다를 방지

**근거**
기능 정의가 법 요건에서 직접 도출된다. 「3대 기본지키기」는 하나라도 누락 시 3개월 내 계약 취소 + 보험료 전액 환급이므로, 판정 대상이 이진적이고 명확하다. 확률적 판정이 필요 없어 D-2의 체크리스트 상태머신과 정확히 정합한다.

<a id="d-8"></a>
## D-8. 데이터셋 탐색 실패 — 판별 기준을 먼저 세우지 않은 대가

**상황**
STT 파인튜닝용 데이터를 찾는 과정에서 **네 번 연속으로 부적합한 데이터셋을 열어봤다.**

| 데이터 | 실제 내용 | STT 적합? |
|---|---|---|
| 금융 상담 QA | 상담 텍스트 QA (instruction/answer) | ✗ 음성 없음 |
| 금융 합성 정형데이터 | 카드·CB 수치 테이블 | ✗ 무관 |
| 금융상품 추천 | 상품추천 Q/CoT/A 텍스트 | ✗ 음성 없음 |
| 상담 음성(KtelSpeech) | wav + 실제 발화 전사 | **✓** |

**판단 (사후 확립한 기준)**
STT 학습 데이터는 두 조건을 모두 만족해야 한다.
1. **데이터 유형이 "음성"** — 앞의 셋은 모두 유형이 "텍스트"였고, 그 한 줄만 봤어도 열어보지 않고 걸러낼 수 있었다
2. **전사가 실제 발화 그대로** — 정제·재작성된 전사는 음성과 1:1로 대응하지 않아 학습에 쓰면 오히려 모델이 손상된다

**근거**
첫 번째 데이터의 전사는 화자 라벨이 꼬여 있고 문장이 매끄럽게 다듬어져 있었다. 겉보기엔 상담 데이터지만 STT 정답으로는 쓸 수 없었다. 반면 KtelSpeech는 `그/`, `자질 자질하게` 같은 간투사·반복이 그대로 살아 있고 `(mobile)/(모바일)` 형태의 이중 표기 규칙이 있어 STT 학습용임이 명확했다.

**부산물**
부적합 판정된 데이터도 버리지 않고 용도를 재배치했다. 상담 QA·상품추천 텍스트는 용어 사전(F-4.1), RAG few-shot, 판정 로직 테스트셋으로 활용 가능하다.

<a id="d-9"></a>
## D-9. LoRA 채택 / QLoRA 미채택

**판단**
LoRA(r=32, q·v 어텐션) 채택. 전체 파라미터의 **1.22%(943만 / 7.7억)** 만 학습.

**근거**
- 8천 건 규모에 풀파인튜닝은 과적합과 원본 성능 손상(catastrophic forgetting) 위험
- 학습이 빨라 하이퍼파라미터 실험을 여러 번 돌릴 수 있음 — 이것이 실제로 exp1~4를 가능하게 했다
- 원본 가중치를 보존하므로 되돌리기 쉬움

**QLoRA를 쓰지 않은 이유**
QLoRA는 VRAM이 부족할 때 4bit 양자화로 메모리를 아끼는 기법이다. 우리 상황은 정반대였다.

| | 값 |
|---|---|
| Whisper medium | 약 7.7억 파라미터 |
| fp16 학습 시 VRAM | 10~20GB |
| 가용 VRAM | **140GB** |

여유가 7배 이상이므로 양자화로 정확도를 손실할 이유가 없다. CER을 낮추는 것이 목표인데 시작부터 정확도를 깎고 들어가는 선택이며, 양자화 오버헤드로 학습이 오히려 느려질 수 있다. 기법을 이력서에 추가하려고 도입하는 것은 목적과 무관하다.

## D-10. 실험 설계 — baseline을 학습 전에 측정

**판단**
학습 코드보다 먼저 **파인튜닝 전 CER 측정**을 파이프라인에 넣었다.

**근거**
학습 후에 재면 baseline이 오염되어 개선폭을 말할 수 없다. "파인튜닝을 했다"와 "얼마나 개선했다"는 전혀 다른 진술이며, 후자만이 검증 가능하다.

**측정 지표**
한국어는 어절 단위 WER보다 **문자 단위 CER**이 실질적인 인식 품질을 반영한다. 조사·어미 변화가 많아 어절 단위로는 미세한 차이도 오류로 계산되기 때문이다.

**실험 기록 자동화**
설정·CER·오류 분해·개선/퇴화 샘플 수를 자동으로 누적하고 마크다운 리포트를 생성하는 트래커를 별도로 작성했다. 수치 하나가 아니라 **"무엇을 바꿨더니 얼마나 달라졌는가"의 이력**이 남아야 개선 근거를 설명할 수 있다.

<a id="d-11"></a>
## D-11. 오류 분해로 개선 방향 결정

**상황**
baseline CER 11.70%. 이 숫자만으로는 무엇을 고쳐야 할지 알 수 없다.

**검토**
오류 샘플을 확인한 결과 세 유형으로 갈렸다.

| 유형 | 예시 |
|---|---|
| 숫자 표기 | 정답 `칠 오 공 이` vs 예측 `7 5 0 2` |
| 구두점·띄어쓰기 | 마침표·물음표 누락 |
| 고유명사·전문용어 | `김창출` → `김창추리` |

**핵심 발견**
숫자 표기와 구두점은 **음성을 잘못 인식한 것이 아니라 표기 규칙이 다른 것**이다. 소리는 정확히 알아들었다.

**판단**
CER을 요소별로 분해하는 평가를 도입했다. 구두점 제거 후 CER, 숫자 제거 후 CER을 각각 측정해 **"순수 인식 오류"** 를 분리했다.

**실험 결과**

| 실험 | 변경점 | CER | 순수 인식오류 | 퇴화 샘플 |
|---|---|---|---|---|
| baseline | — | 11.70% | — | — |
| exp1 | LoRA r32 | 6.92% | 5.97% | 35건 |
| exp2 | + eval / best checkpoint | 6.72% | 5.94% | 29건 |
| exp3 | + beam search(5) | **6.30%** | — | — |

**해석**
- 개선분의 대부분은 **도메인 표기 규칙 학습**에서 발생했다. 숫자 표기 오류 기여도는 0.05%p 수준까지 떨어져 사실상 해소되었다
- 반면 순수 인식 오류는 5.97% → 5.94%로 **거의 움직이지 않았다**. 학습 파라미터 조정으로는 한계에 도달했다는 신호
- exp2의 valid loss 곡선(0.251 → 0.268 → 0.321)이 과적합을 직접 증명했다. epoch 1이 최적이었고, exp1은 3 epoch 종료 상태를 그대로 사용해 퇴화 샘플 35건이 발생했다
- exp3은 학습 없이 디코딩 전략만 바꿔 0.42%p를 얻었다. 발화당 0.6초로 준실시간 청크 방식에 적용 가능한 수준이어서 실서비스에 반영 가능하다

<a id="d-12"></a>
## D-12. train-serving skew — 학습 환경과 서비스 환경의 음향 차이

**상황**
파인튜닝을 마친 뒤, 학습 데이터의 음향 특성이 실제 서비스와 다르다는 점을 확인했다.

| | 학습 데이터(KtelSpeech) | 실제 서비스 |
|---|---|---|
| 경로 | 전화망(PSTN) | WebRTC 브라우저 마이크 |
| 대역 | 8kHz 협대역 (300~3400Hz) | 16kHz 이상 광대역 |
| 코덱 | G.711/AMR | Opus |

**검토**
파인튜닝 효과가 그대로 전이된다고 가정할 수 없다. 다만 D-11의 오류 분해 결과가 판단 근거가 되었다.

| 학습된 것 | 전이 가능성 |
|---|---|
| 표기 규칙(숫자·구두점) | 높음 — 음향과 무관 |
| 한국어 상담체 말투·금융 어휘 | 높음 |
| 전화망 음향 적응 | **불확실** |

개선분의 대부분이 표기 규칙 쪽이었으므로 전이 가능성이 높다고 보았으나, 이를 추측으로 두지 않기로 했다.

**판단**
**실제 서비스와 동일한 오디오 경로로 A/B 평가셋을 별도 구축**한다.
- 브라우저 getUserMedia → 16kHz 모노 PCM (서비스 STT 입력과 동일 규격)
- 대본은 고지 항목 기반 발화 → 읽은 문장이 곧 정답 전사이므로 전사 작업 불필요
- 같은 녹음을 baseline과 파인튜닝 모델에 동일하게 투입하는 A/B 구조이므로 녹음 장비 차이는 상쇄됨

**한계 명시**
대본 낭독은 실제 상담보다 쉽다(끊김·간투사 없음). 따라서 이 평가셋의 CER은 실서비스보다 낙관적이며, **전이 여부 판정에는 유효하나 절대 성능 예측에는 사용하지 않는다.**

<a id="d-13"></a>
## D-13. 개선 중단 시점 판단 — 세 축을 모두 검증한 뒤 종료

**상황**
CER 6.30%(exp3)에서 순수 인식 오류가 5.9%대에 정체되어 있었다. 여기서 멈출 것인가, 계속 밀 것인가. "제품 가치가 낮으니 중단"은 추측이므로, 정체 원인을 실험으로 확인한 뒤 판단하기로 했다.

**검토 — 세 가지 후보 축**

| 축 | 검증 실험 | 결과 |
|---|---|---|
| 모델 용량 | exp4 (rank·모듈 확장) | 처음엔 기각 → **재검증으로 뒤집힘** |
| 학습률 | exp5(2e-4) / exp6(1e-4) | exp5가 최적, 축 소진 |
| 데이터 양 | exp7 (8000→16000) | 유효, 축 계속 열려 있었음 |

**exp4의 초기 결론이 틀렸던 이유**

exp4는 rank 32→64와 대상 모듈 2→4개를 **동시에** 바꿨고, 그마저 이후 과다로 판명된 학습률(1e-3)에서 실행됐다. 그 결과 CER이 8.09%로 악화되어 "용량은 병목이 아니다"라고 결론 내렸는데, 이 결론은 교란변수 위에 서 있었다.

exp5에서 학습률 2e-4가 최적임을 확인한 뒤, **exp4와 동일한 용량 설정(r64, q·k·v·out)을 학습률만 2e-4로 바꿔 재검증(exp8)** 했다.

| | 용량 | 학습률 | valid 최저 | CER |
|---|---|---|---|---|
| exp4 | r64, q·k·v·o | 1e-3 | 0.338 | 8.09% |
| exp8 | r64, q·k·v·o | **2e-4** | **0.2232** | **5.43%** |

동일한 용량인데 학습률 하나로 결과가 정반대가 되었다. **exp4의 실패 원인은 용량이 아니라 학습률 과다였다.** 초기 결론을 뒤집었다.

**용량 축을 한 단계 더 (exp11)**

용량이 유효한 것으로 밝혀졌으므로 r128까지 확장해보았다. 200샘플 평가에서는 5.38%로 exp8(5.43%)보다 근소하게 나아 보였다.

**측정 방법의 함정 — 200샘플 vs 500샘플**

exp9(디코딩 파라미터 탐색)에서 0.02%p 차이가 측정 노이즈임을 이미 확인한 바 있다. exp8과 exp11의 차이(0.05%p)도 같은 범주일 수 있다고 보고, 최종 후보 4개를 **valid 전체 500샘플로 재측정**했다.

| 모델 | 200샘플 | 500샘플 |
|---|---|---|
| exp5 (r32, 8k, lr1e-3) | — | 6.05% |
| exp7 (r32, 16k) | 6.02% | 5.86% |
| **exp8 (r64, 16k)** | 5.43% | **5.56%** |
| exp11 (r128, 16k) | **5.38%** | 5.74% |

**순위가 역전됐다.** 200샘플에서는 exp11이 앞섰지만 500샘플에서는 exp8이 확실히 앞섰다. 표본이 부족하면 0.05%p 차이는 판별할 수 없으며, 재측정하지 않았다면 더 무겁고 더 나쁜 모델(r128)을 최종으로 채택했을 것이다.

**최종 채택**

**exp8 (LoRA r64, q·k·v·out, lr 2e-4, 학습 데이터 16000건)**
CER **11.70% → 5.56%, 52.4% 개선.** 용량은 r64에서 포화하며, 그 이상은 같은 데이터 규모에서 과적합으로 전환된다.

**판단 — 여기서 종료**

세 축(용량·학습률·데이터) 모두 검증했다.
- 용량: r64가 최적, r128은 악화 (exp8 vs exp11)
- 학습률: 2e-4가 최적, 위아래 모두 악화 (exp5 vs exp1·exp6)
- 데이터: 8000→16000은 유효했으나(exp7), 추가 확장은 재추출·재학습 비용 대비 남은 순수 인식오류가 도메인 특성(말 끊김·간투사·겹말·저음질, 전사자 간 3~5% 불일치)에 가깝다고 판단

**근거 — 제품 관점**
이 시스템의 목적은 완벽한 전사가 아니라 **고지 항목의 언급 여부 판정**이다. 판정 로직이 키워드와 의미 유사도 기반이라 표기가 다소 달라도 매칭은 성립한다. 3주 일정에서 추가 실험에 시간을 더 쓰는 것은 프로젝트 본체(F-2 실시간 판정 로직, 파트 간 인터페이스)를 위협한다.

**이 항목의 의미**
중단은 추측이 아니라 세 축을 실제로 밀어본 뒤의 판단이다. 그 과정에서 두 가지를 배웠다. 하나는 **실패한 실험(exp4)의 결론을 교란변수를 의심해 재검증하고 뒤집은 것**이고, 다른 하나는 **작은 표본(200)에서 확정한 순위가 큰 표본(500)에서 역전된 것을 재측정으로 잡아낸 것**이다. 두 경우 모두 첫 결과를 그대로 믿었다면 틀린 모델을 최종으로 골랐을 것이다.

앞의 세 사례는 **외부에서 주어진 조건**(인프라, API 사양, 데이터 출처)을 의심한 것이고, 네 번째는 **자신이 직접 낸 실험 결론**을 의심한 것이다. 후자가 더 어렵다. 실패로 보이는 결과를 받아들이고 다음으로 넘어가는 것이 자연스러운데, "이 실패가 진짜 원인 때문인가"를 한 번 더 물어야 하기 때문이다. D-13에서는 여기에 더해 표본 크기(200 vs 500샘플)가 순위를 오판시킬 수 있다는 것까지 확인했다. 두 검증 모두, 첫 결과를 그대로 믿었다면 다른 결론(더 무거운 모델, 잘못된 원인 진단)에 도달했을 것이다.
